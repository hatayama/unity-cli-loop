# Package Manager Distribution

## Channel policy

The Homebrew tap (`hatayama/homebrew-tap`) updates on every dispatcher release,
including beta tags. There is no separate stable-only formula yet.

## Components

| Piece | Role |
| --- | --- |
| `hatayama/homebrew-tap` / `Formula/uloop.rb` | Published formula. Generated by release automation — do not edit by hand. |
| `cli/release-automation/cmd/update-homebrew-formula` | Renders the formula from the dispatcher release assets and pushes it to the tap. |
| `.github/workflows/dispatcher-publish.yml` `post-publish` step | Runs the update command after a successful dispatcher publish. |
| `HOMEBREW_TAP_TOKEN` repository secret | Fine-grained PAT scoped to `hatayama/homebrew-tap` with Contents Read and write. Used only for tap writes; release asset reads use the workflow `GITHUB_TOKEN`. |

## Operations

- When `HOMEBREW_TAP_TOKEN` is unset, the update command logs an explicit skip and
  exits 0 so the dispatcher release still succeeds.
- A red `post-publish` Homebrew step does not affect already-uploaded release
  assets. Re-run that workflow run; formula updates are idempotent.
- `uloop update` refuses Homebrew-managed installs and directs users to
  `brew upgrade uloop`. The dispatcher freshness path does the same for required
  updates and skips optional auto-updates.
- The Unity Settings window and the Setup Wizard offer no CLI action for a
  Homebrew-managed install: the primary button is disabled and reads
  `Managed by Homebrew`. Installing from Unity would place a second, package-owned
  binary in `~/.local/bin` while brew keeps its own on PATH. When such an install is
  below the pin minimum, the status line names the required version and
  `brew upgrade uloop` so the disabled button is not a dead end.

## Known follow-ups

1. After a stable channel exists, decide whether formula updates should gate on
   non-prerelease tags or whether a separate `uloop@beta` formula is needed.
   Until then, beta releases keep advancing the single formula.
2. winget support is planned for the stable-release preparation window. New
   packages in winget-pkgs wait on human moderation (typically several business
   days to about two weeks), so the intended order is: quietly cut the stable
   tag → land the first winget PR → announce externally.
